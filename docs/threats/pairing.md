# Threats: pairing with accounts and notes

Rows start `planned` and flip to `mitigated` when their test lands; same columns and status words as [threat-model.md](../threat-model.md). Owner stream: P1 (present server); the pairing rules are in ADR 0015.

| id | STRIDE | threat | L | I | mitigation | test | status |
|---|---|---|---|---|---|---|---|
| PAIR-14 | S | Reverse QRLjacking: an attacker relays their own screen's QR so a signed-in victim approves onto it | med | high | The phone shows three 2-digit choices and the user taps the one on the screen in front of them; a wrong tap cancels the claim and the screen gets a new code | `PAIR-14 match` | planned |
| PAIR-15 | D | A stranger spends a live code, or probes whether a code exists, without an account | med | med | The claim reads the cookie before the Directory lookup, which answers a signed-out owner of a live code `auth_required` without routing, so nothing is spent; a right code is no miss, so a venue's phones behind one address are never locked out, while a wrong code is. A guest claim the drop refuses (`GUEST_DROP` off, or pass, since a claim carries no pass) answers that refusal unrouted for any code but a demo one, whether it exists or not, so it is no oracle, and counts no miss, so a phone that falls back to a guest claim in a room with no guests is never locked out. Residual: while no sign-in is configured (the mock source) every phone counts as signed in, and no cookie is read; under `GUEST_DROP=open` a signed-out stranger may claim a live code as a guest, as the drop intends (DROP-06 bounds what a guest can do); with guests refused, a guest claim still routes a demo code uncounted, so demo codes can be probed as a guest at the `RL_CLAIM` rate (20 a minute per address), accepted since demo codes are public by design and short-lived; a signed-out owner can poll a live code it already knows without the miss counter, which gains a prober nothing, since wrong guesses still count and a blocked address is refused before any code is read | `PAIR-15 auth-first`, `PAIR-15 lookup who` (unit), `PAIR-15 guest refusal` | planned (until commit 5 removes the mock's stand-in) |
| PAIR-16 | I | The screen's view leaks a file id, user id or email | low | high | `ScreenView` carries only the display flags (`derived` copied key by key); the phone-only extras and the pick's choices are added in `phoneView` alone. A test pins its exact key set at every depth and that no value is a file, version, user, sign-in or session id | `PAIR-16 view` | mitigated |
| REL-14 | T | A retried create (a lost claim answer) does the work twice, so the phone reads its own claim as `code_taken` | med | med | Idempotency-Key (idem.ts): the Screen keeps each key's first claim answer, and a pairing's first match answer, through `seams/pairing/idem.ts`, bounded and shape-checked on wake, dropped after 24 h and when the pairing or the session ends, and a replay answers only a pid the current pairing still holds. A claim's key is scoped to one person, never the address (one address is shared by a room): the signed-in account, else the tab's `X-Bloop-Nonce` (32 random bytes the phone keeps in sessionStorage) under its own `HASH_PEPPER` sub-key (info `bloop device`), so a replay follows a phone across networks and two phones behind one address share nothing; with neither, the key is not read and the claim replays nothing. Every claim with one key gets the first's answer and pid, whatever the interleaving: the Screen takes one flight per key and, with no flight, reads the row again before claiming, since the route's lookup may have run before the first saved it (`oneFlight`). A match's key is scoped to the pairing. A claim's row never holds the pid: it keeps a nonce the secret is derived from by HMAC under a sub-key HKDF draws from `HASH_PEPPER` (info `bloop pid`), so a leaked row names no credential and no other HMAC under the pepper shares its key; every one of those reads an input that cannot start `pid:` besides. A rotated pepper only breaks replays inside the 24 h window. A replay answers it and changes nothing | `REL-14 adapter`, `REL-14 adapter purge`, `REL-14 adapter no secret`, `REL-14 pepper domains` (unit), `REL-14 claim owner` (`/api/claim`: per account, per tab nonce across networks, none without either, an ended pairing never replays), `REL-14 claim single flight`, `REL-14 match replay` (`/api/match`); still to come on `/api/screens` and `/api/screen/link` | planned |
| NOTES-01 | I | Speaker notes reach the screen | low | high | The notes route answers only a pairing's pid, live, and `no-store`; no frame, link or bundle carries notes. Notes come only from the pinned user's own library files; a guest-dropped file shows none | `NOTES-01 phone-only` | planned |
| REL-13 | T | A late screen report from before a page turn rewinds the slide the phone and the screen show | med | low | Each sender's `seq` is kept, and a report not above the last applied one changes nothing; a screen report carries `base`, the `v` of the view it was built on, and one from before the phone's latest turn changes nothing. The server half is P1's; the screen sends `base` from P2 | `REL-13 an older seq never rewinds shown`, `REL-13 cross-sender` | planned |
| REL-16 | R | A live start that fails leaves no trace, so a broken screen path goes unseen | med | med | Approval sets a start deadline 15 s out; the first fetch or screen report writes one `start` point (ok), the deadline writes one with its cause; no user, file or screen id | `REL-16 a failed start writes one data point with a cause and no personal data`, `REL-16 fetch_refused` | planned |
| REL-18 | I | A Revoke sent while the screen is offline leaves the slide on the wall until the viewer parks, up to 60 s | med | low | Every link is revoked at once, so nothing new loads during the offline grace; the slide already decoded stays until the grace ends (residual, stated in the phone's Revoke copy) | `REL-18 offline grace` | planned |
