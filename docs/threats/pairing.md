# Threats: pairing with accounts and notes

Rows start `planned` and flip to `mitigated` when their test lands; same columns and status words as [threat-model.md](../threat-model.md). Owner stream: P1 (present server); the pairing rules are in ADR 0015.

| id | STRIDE | threat | L | I | mitigation | test | status |
|---|---|---|---|---|---|---|---|
| PAIR-14 | S | Reverse QRLjacking: an attacker relays their own screen's QR so a signed-in victim approves onto it | med | high | The phone shows three 2-digit choices and the user taps the one on the screen in front of them; a wrong tap cancels the claim and the screen gets a new code | `PAIR-14 match` | planned |
| PAIR-15 | D | A stranger spends a live code, or probes whether a code exists, without an account | med | med | The claim reads the cookie before the Directory lookup, which answers a signed-out owner of a live code `auth_required` without routing, so nothing is spent, and counts it as a miss. Residual: while no sign-in is configured (the mock source) every phone counts as signed in | `PAIR-15 auth-first` | mitigated |
| PAIR-16 | I | The screen's view leaks a file id, user id or email | low | high | `ScreenView` carries only the display flags (`derived` copied key by key); the phone-only extras and the pick's choices are added in `phoneView` alone. A test pins its exact key set at every depth and that no value is a file, version, user, sign-in or session id | `PAIR-16 view` | mitigated |
| REL-14 | T | A retried create (a lost claim answer) does the work twice, so the phone reads its own claim as `code_taken` | med | med | Idempotency-Key (idem.ts): the Screen keeps each key's first claim answer through `seams/pairing/idem.ts`, bounded and shape-checked on wake, dropped after 24 h and when the pairing or the session ends. A claim's row never holds the pid: it keeps a nonce the secret is derived from under `HASH_PEPPER`, so a leaked row names no credential. A replay answers it and changes nothing | `REL-14 adapter`, `REL-14 adapter purge`, `REL-14 adapter no secret` (unit), `REL-14 an Idempotency-Key replay returns the first answer` (`/api/claim`); still to come on `/api/screens` and `/api/screen/link` | planned |
| NOTES-01 | I | Speaker notes reach the screen | low | high | The notes route answers only a pairing's pid, live, and `no-store`; no frame, link or bundle carries notes. Notes come only from the pinned user's own library files; a guest-dropped file shows none | `NOTES-01 phone-only` | planned |
| REL-13 | T | A late screen report from before a page turn rewinds the slide the phone and the screen show | med | low | Each sender's `seq` is kept, and a report not above the last applied one changes nothing; a screen report carries `base`, the `v` of the view it was built on, and one from before the phone's latest turn changes nothing. The server half is P1's; the screen sends `base` from P2 | `REL-13 an older seq never rewinds shown`, `REL-13 cross-sender` | planned |
| REL-16 | R | A live start that fails leaves no trace, so a broken screen path goes unseen | med | med | Approval sets a start deadline 15 s out; the first fetch or screen report writes one `start` point (ok), the deadline writes one with its cause; no user, file or screen id | `REL-16 a failed start writes one data point with a cause and no personal data`, `REL-16 fetch_refused` | planned |
| REL-18 | I | A Revoke sent while the screen is offline leaves the slide on the wall until the viewer parks, up to 60 s | med | low | Every link is revoked at once, so nothing new loads during the offline grace; the slide already decoded stays until the grace ends (residual, stated in the phone's Revoke copy) | `REL-18 offline grace` | planned |
